# Google Sheets ERP Mirror v1

ERP Mirror v1 gives owners and accountants a readable, near-real-time copy of
selected committed ERP transaction facts in Google Sheets. PostgreSQL remains
the accounting authority and recovery source. The sheet is a reporting mirror;
do not use it to edit ERP balances or transaction state.

The mirror starts with new eligible transactions recorded after the connection
is configured. Those transactions enter the durable outbox immediately, even
while the connection test is pending, and remain held until that exact
configuration is verified. Code30.2 does not backfill historical ERP or
spreadsheet rows. Keep the existing workbook tabs as their historical archive
and reconcile them separately from the new append-only feed.

The integration uses one bound Apps Script and one fixed tab named
**ERP Mirror v1**. It does not modify other tabs.

## Safety model

- The backend writes each event to a tenant-scoped PostgreSQL outbox inside the
  same transaction as the business change.
- An active configuration that has not passed its current connection test keeps
  ordinary business rows pending without consuming delivery attempts. Only its
  connection-test rows can leave the outbox until verification succeeds.
- A background dispatcher leases committed events and retries temporary network,
  throttling, and Google failures with capped exponential backoff.
- Every request is HMAC-SHA256 signed with a tenant-specific secret. The Apps
  Script rejects unsigned, altered, or unsupported envelopes.
- The ERP stores that signing secret only as company-bound AES-256-GCM
  ciphertext. Production uses a dedicated encryption key generated by the
  deployment tooling; the ordinary settings/status APIs never return the
  plaintext secret.
- The Apps Script takes a script lock, validates the exact v1 header layout, and
  appends accepted events. It never updates or deletes an accepted event.
- Retries are idempotent on `event_id` plus the canonical payload SHA-256. The
  same ID and hash returns `duplicate`; the same ID with different bytes fails.
- Text that could be interpreted as a spreadsheet formula is forced to text.
- Paid-order events leave the Customer column blank and omit customer names,
  phone numbers, and IDs. Invoice and order identity remains in the reference
  and source columns, which is sufficient for financial reconciliation without
  exporting unnecessary identity data to a potentially link-shared workbook.
- A paid order is mirrored as one revenue row. Its cash, card, UPI, QR, and
  wallet columns are an exact breakdown of that same amount, including split
  tenders; they are not additional revenue rows.
- The backend sends only to approved HTTPS Google Apps Script hosts and validates
  every redirect before following it.

## Client boundary

Only the ERP backend may deliver mirror events. The web POS and Reports screens
do not store an Apps Script URL or post financial data from the browser. They
keep their normal receipt, print, and CSV behavior while the server mirrors
eligible committed transactions through the outbox.

The source under `frontend/ios` is compiled into the `App` Xcode target, but it
is an archived prototype: `frontend/CAPACITOR.md` and `docs/DISTRIBUTION.md`
exclude it from CI, signing, partner distribution, production deployment, and
the supported release workflow. Its retained Integrations view is read-only: it
loads `settings/google-sheets` from the authenticated ERP API and never stores a
webhook, copies a script, or sends data to Apps Script directly. This boundary
must remain in place if iOS distribution is introduced later.

## Visible columns

The fixed v1 schema has 33 columns:

1. Received At
2. Occurred At
3. Event Type
4. Event ID
5. Event Key
6. Company ID
7. Branch
8. Reference / Invoice
9. Description
10. Customer
11. Quantity
12. Amount Minor
13. Payment Method
14. Cash Minor
15. Card Minor
16. UPI Minor
17. QR Minor
18. Wallet Minor
19. Actor / Cashier
20. Status
21. Source Type
22. Source ID
23. Source Revision
24. Schema Version
25. Payload SHA256
26. Period Start
27. Period End
28. Currency
29. Gross Revenue Minor
30. Net Revenue Minor
31. Expense Total Minor
32. Net Profit Minor
33. Payload JSON

Money is stored in integer minor units to preserve exact accounting values. For
GBP, INR, and other two-decimal currencies, `12345` means `123.45`. Build display
or dashboard tabs from the mirror and divide minor-unit values by 100 there.

Code30.2 transaction producers leave the period and report-total columns blank.
Those columns are reserved for a future explicit summary event and must not be
treated as an independently generated P&L. Current dashboards should calculate
their totals from the mirrored transaction rows and reconcile them to the ERP.

## Setup

### 1. Add the Apps Script

Open the target Google Sheet, then choose **Extensions → Apps Script**. Replace
the editor contents with the exact file at
`integrations/google-sheets/Code.gs`, save it, and deploy it as a Web app:

| Field | Value |
|---|---|
| Type | Web app |
| Execute as | Me |
| Who has access | Anyone with the link |

The public URL is safe only because every event must carry a valid HMAC. Google
will ask the sheet owner to authorize the bound script.

Copy the `/exec` Web app URL. It should use `https://script.google.com`.

### 2. Configure the ERP

Open **Settings → Google Sheets**, enter the Web app URL, and configure the
mirror. The ERP shows a new signing secret on initial setup, every URL change,
or explicit rotation. Copy it immediately; ordinary status responses never
expose it.

### 3. Add the Script Property

In Apps Script, open **Project Settings → Script Properties** and add:

| Property | Value |
|---|---|
| `D_COMPANY_ERP_MIRROR_HMAC_SECRET` | The signing secret returned by the ERP |

Do not put the secret in `Code.gs`, a sheet cell, source control, screenshots, or
support messages.

### 4. Test and verify

Use the ERP connection test. It queues a real signed outbox event. Confirm that:

- the status reports a delivered event;
- the **ERP Mirror v1** tab appears with exactly 33 headers; and
- one `mirror.connection_test` row is appended.

Business entries created after configuration may already show as **Held for
verification**. They remain durable in PostgreSQL and become eligible for
delivery only after the current test row succeeds. A test queued before a URL
or secret correction cannot verify the corrected connection.

The dispatcher normally delivers within a few seconds. A passing health page or
saved URL alone does not prove that the sheet accepted an event.

## Operating the mirror

Create pivot tables, charts, reconciliations, and accountant-facing views in
separate tabs that reference **ERP Mirror v1**. Do not rename its headers, add
columns inside it, or edit its event IDs and hashes; the sink fails closed when
the v1 schema changes.

When a temporary failure exhausts its retry budget, the event is quarantined and
remains in PostgreSQL with its payload, hash, attempts, and last error. Fix the
URL, Script Property, quota, or header issue, then use the owner retry control.
The sink deduplicates a delivery that reached Google before the acknowledgement
was lost.

Rotating the secret immediately invalidates the previous value and resets
verification. Update the Script Property with the newly returned secret and
send a new test. Business entries already held by an unverified setup stay in
the same durable generation and are released only by the post-rotation test.

Changing the Apps Script URL always creates and returns a fresh one-time secret.
While a connection is still unverified, correcting its URL preserves its held
business entries and requires a new test. Once a connection is verified, the
ERP refuses URL or secret changes while current-generation business entries are
pending, leased, or quarantined. Let waiting work drain and retry failed entries
before changing the connection; this prevents an immutable business fact from
being silently abandoned or retargeted to another generation.

Back up the production `GOOGLE_SHEETS_SECRET_ENCRYPTION_KEY` with the other
server secrets. Losing it does not alter ERP transactions or existing sheet
rows. Restore the key from the encrypted production backup so pending deliveries
can drain; do not bypass their immutable generation by pointing them at a new
destination.

Disconnecting stops delivery and removes the active destination credentials. It
does not delete rows already in Google Sheets or erase PostgreSQL delivery
history. The ERP refuses to disconnect while current-generation business rows
remain undelivered; drain or retry them first.

## Troubleshooting

**`secret_not_configured` or `signature_invalid`**

Set the exact current ERP signing secret in the
`D_COMPANY_ERP_MIRROR_HMAC_SECRET` Script Property. Do not add quotes or spaces.

**`header_mismatch`**

The existing **ERP Mirror v1** tab does not have the exact v1 headers. Preserve
the tab for evidence, create a new target sheet, deploy the script there, and
update the ERP URL. Do not rewrite historical rows in place.

**Events remain pending**

Check the backend dispatcher is running, the database migrations reached the
current head, and outbound HTTPS can reach `script.google.com` and the validated
Google redirect host.

**Events are quarantined**

Read the owner-visible last error, correct the cause, and retry quarantined
events. Authentication, event/hash conflicts, unsupported schema, and invalid
destinations require correction rather than blind retries.

**A row is missing after a reported delivery**

Search by Event ID, not description or invoice. If PostgreSQL marks the event as
delivered but that exact ID is absent, preserve both sides as evidence and
investigate before manually copying values.

## Versioning

The schema identifier is `erp-mirror.v1`. Changing headers, signed fields, hash
rules, or payload interpretation requires a new version and migration plan. Do
not silently repurpose a v1 column or relax HMAC/header validation.
